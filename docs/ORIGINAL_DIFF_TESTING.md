# 원본 대조(차분) 검증 환경 — Scorched Earth v1.5 (DOSBox-X)

웹 재구현 엔진이 원본 `SCORCH.EXE` 와 같은지 대조하기 위해, 원본을 에뮬레이터 안에서만 돌려 **결정론적 골든 데이터**를 뽑는 환경. 작성일 2026-11-16. "확인 못 함"으로 적은 것은 실제로 검증하지 못한 것이다.

## 1. 구성과 환경

| 항목 | 값 |
|---|---|
| 에뮬레이터 | DOSBox-X **2026.10.01** (winget `joncampbell123.DOSBox-X`, 설치 위치 `C:\DOSBox-X\dosbox-x.exe`, 설치 관리자 해시 검증됨) |
| 원본 | `_reference\scorch_original`(손대지 않음) -> 복사본 `_reference\dosbox_run\game`(EXE 바이트 동일 확인) |
| 설정 | `_reference\dosbox_run\dosbox_scorch.conf` (사본: `tests\golden\scenario_001.dosbox.conf`) |
| CPU | `core=normal`, `cputype=486`, `cycles=fixed 30000` (속도 자동조절 없음) |
| 네트워크/장치 | `ne2000=false`, `ipx=false`, serial/parallel `disabled`, 사운드·MIDI·GUS 없음. 에뮬레이터 안에서만 실행, 호스트 네트워크 설정 변경 없음 |
| 스크립트 | `_reference\tools\diff\` (Python 은 `-I`) |

- 원본은 게임 실행 중 `SCORCH.CFG`/`SCORCH.MKT` 등을 복사본 폴더에만 쓴다. 복사본 폴더의 `SCORCH.CFG` 는 `tests\golden\scenario_001.SCORCH.CFG` 와 같다.
- 게임 옵션: `FAST_COMPUTERS=on`(RE §3.3 의 정본 분기 = dt 0.02, BogoMips 보정 없음), `TRACE=on`(투사체 경로가 VRAM 에 남아 추출 가능), `SOUND=off`, `FLY_SOUND=off`. 나머지는 기본값. 이 값들의 on/off 표기가 원본 파서에서 대소문자 구분 없이 동작하는지는 확인 못 함(소문자 `on` 이 실제로 적용됨은 확인: 상태 화면의 Trace 경로가 그려지고 지형·풍속이 재현됨. FAST_COMPUTERS 적용 여부 자체는 화면으로 직접 확인 못 함).

## 2. 결정론 (RNG 시드 고정)

시드는 `time()` 하위 16비트(RE §9). 호스트 시계를 건드리지 않고 **게임 안에서** 고정한다.

- `make_harness.py` 가 16비트 DOS 상주 프로그램 `HARNESS.COM` 을 직접 바이트코드로 조립한다(외부 어셈블러 불필요).
- INT 21h `AH=2Ch`(시각)/`2Ah`(날짜)를 가로채 **1995-06-04 10:30:21.00** 로 고정 응답. 인자 `--h --m --s` 로 바꿀 수 있다.
- 검증: 초만 21 -> 22 로 바꾸면 지형·풍속이 달라지고(풍속 49 -> 76), 같은 시각이면 매번 같다 -> 시드 제어가 실제로 작동함. 실제 시드 숫자(= unix 시각 하위 16비트, Borland 시간대 규칙 포함)는 **확인 못 함**.
- DOSBox-X 쪽 시간 고정 옵션(`synchronize time`)은 쓰지 않는다(호스트 시계 동기화 끔이 기본). BIOS tick(0040:006C)은 에뮬 시간이라 호스트 속도와 무관하게 진행하지만 부팅 시점마다 값이 다를 수 있다(아래 재현성 참고).

## 3. 입력 자동화

호스트 쪽 SendKeys/PostMessage 는 쓰지 않는다. 시도 결과: PostMessage 는 SDL 이 무시, SendKeys 는 창이 전면일 때만(전면 전환 자체가 Windows 에서 막힘) 동작해 불안정하고, 사용자 데스크톱에 영향을 주므로 폐기.

대신 `HARNESS.COM` 이 INT 16h(원본의 `Bios Keyboard` 옵션이 기본 ON 이라 BIOS 키보드 사용)를 가로채 **스크립트 키를 지정한 tick(18.2Hz, 에뮬 시간) 간격으로 주입**한다. 스크립트가 끝나면 실제 키보드로 연결된다.

스크립트: JSON 리스트 `[[대기_tick, "키"], ...]`. 키 = 한 글자, `ENTER ESC UP DOWN LEFT RIGHT SPACE TAB BS PGUP PGDN F1..F10`, 또는 `dump`. 원본 조작(RE §3.1)은 확인됨: `LEFT/RIGHT` 각도 -1/+1(LEFT 가 줄임을 실측), `UP/DOWN` 파워 ±1, `PGUP/PGDN` 파워 ±15, `ENTER` 발사.

## 4. 관측 수단

`dump` 항목은 INT 16h 후크 안에서 `D<n>.BIN`(게임 폴더) 을 쓴다. 에뮬 시간은 거의 흐르지 않으므로 게임 상태를 흔들지 않는다. 형식(918,288 바이트):

`헤더 16(SDMP + 호출자 DS u16 + 예약) + VGA 팔레트 768(6비트) + VGA 4플레인 x 64KB + 기본 메모리 0000:0000~9FFF:FFFF 640KB`

- 화면: 기본 그래픽 모드 360x480x256(unchained). 픽셀 (x,y) = 플레인 `x%4`, 오프셋 `y*90 + x//4`. `dumplib.py` 가 인덱스 색 배열/PNG 로 렌더(눈으로 검증 완료: 메뉴·플레이어 설정·전장 화면 모두 정상 렌더).
- 메모리: 호출자 DS = 원본 데이터 세그먼트(`DS*16` 이 선형 기준). 실측으로 확인한 주소:
  - 풍속 `DS:0x515A` (int16) — 화면 표시 49 와 일치 확인(RE §3.2 와 일치).
  - 탱크 레코드 배열 `DS:0xD568`, 레코드 크기 `0xCA`: x=+0x12, y=+0x14, 각도=+0x92, 파워=+0x9E (RE §3.1 과 일치 확인). 배열 위치/크기는 이 빌드의 실측 값이며 EXE 정적 분석으로 확인한 것이 아니다.
  - 에너지(HP) 필드: +0xA2 또는 +0xA6 이 100 이다. **어느 쪽이 HP 인지 확인 못 함**(시나리오 1 은 탱크가 맞지 않음). 피격 시나리오를 한 번 돌려 변하는 쪽을 보면 확정된다.
- 관측 가능 여부 판단:
  1. 투사체 경로: `TRACE=on` 이면 경로 픽셀이 VRAM 에 남음 -> 전/후 VRAM 차이로 추출 가능(구현·확인됨). 단 **시간 순서**는 없고 픽셀 집합이다. 프레임별 위치는 추출 못 함(투사체 레코드 `DS:0xCEB8` 을 비행 중 샘플링하려면 타이머 후크가 필요, 미구현).
  2. 분화구: 전/후 흙(0x50~0x68) 픽셀 차이로 추출(구현·확인됨).
  3. 탱크 HP: 메모리 덤프에서 가능, 필드 확정만 남음(위 참고).
  4. 지형 생성: 열별 흙 구간 추출(구현·확인됨).
- DOSBox-X 디버거: 사용 불가로 판단. 이 빌드에서 Alt+Pause 를 누르면 DOSBox-X 프로세스가 종료됨(2회 재현). 문서상 `mcp_server`(127.0.0.1 TCP 디버거) 옵션이 있으나 실제로 7777 포트를 열지 않았고 바이너리에도 구현 문자열이 없음 -> 이 빌드에서는 미지원으로 판단. 네트워크 비활성 원칙에 따라 더 시도하지 않음.

## 5. 재현 명령

```
# 시나리오 1 골든 생성 (약 1분 40초, 끝나면 dosbox-x 를 종료함)
bash _reference/tools/diff/capture_golden.sh tests/golden/scenario_001.script.json tests/golden/scenario_001 100
# (BEFORE_IDX/AFTER_IDX 환경변수로 비교할 dump 번호 지정, 기본 1/2)
# 임의 덤프를 PNG 로: python -I _reference/tools/diff/render_all.py <출력폴더> <접두어>
# 시드 고정 시각 변경: HARNESS_ARGS="--s 22" bash .../capture_golden.sh ...
```

- 사전 조건: `HARNESS.COM`(생성기가 자동 작성)과 `dosbox_run\game\SCORCH.CFG` 가 있어야 함. `dosbox_scorch.conf` 의 `[autoexec]` 는 `harness` -> `scorch` 순서.
- 주의: `run_scenario.sh` 는 시작할 때 `dosbox-x.exe` 프로세스를 전부 종료(`taskkill`)한다.
- 대기 시간은 에뮬 속도에 좌우되는 호스트 쪽 sleep 이다. 환경이 느리면 `capture_golden.sh` 3번째 인자(초)를 늘린다.

## 7. 재현성 결과

같은 스크립트를 **별도 프로세스로 2회** 실행해 비교:

- 골든 JSON(시나리오 이름 필드 제외): **동일**. 전/후 픽셀 파일: **동일**.
- 덤프 4개(D0~D3) 전체에서 VGA 팔레트·VGA 4플레인: **바이트 동일**.
- 기본 메모리 640KB: 32~60 바이트만 다름 — BIOS tick 카운터(0000:046C~046D)와 선형 주소 0x6A0xx 대의 몇 바이트(정체는 확인 못 함, 게임 데이터 세그먼트 밖). 탱크 레코드·풍속 값은 동일(JSON 이 동일하므로).
- 2회만 확인했다. 장시간 반복이나 다른 호스트에서의 재현은 확인 못 함.

## 8. 한계 / 확인 못 한 것

- 대조 엔진 쪽 비교는 아직 안 했다. 시도: `tools\diff\seedscan.mjs` 로 엔진의 `createGame(seed)` 지형을 시드 0..65535 전수와 비교 -> 일치 없음(최대 3/360 열, 우연 수준). 원인은 확인 못 함: 원본 화면 좌표(상태바 16행, 테두리)와 엔진 좌표계 오프셋, 원본은 CAVERN 인데 엔진은 하늘 종류 규칙이 달라 보이는 점, 엔진 지형 생성이 추정 구현인 점 중 무엇인지 분리 못 함. 즉 "엔진 불일치 증명"도 "일치"도 아니다.
- 원본의 실제 시드 값 미확인(2항). 엔진 시드와 매핑하려면 R250 상태를 덤프에서 찾아 역산하거나 Borland `time()` 의 시간대 규칙을 확정해야 한다.
- 투사체 시간 순서/프레임별 좌표, 폭발 반경 외 다른 무기, 탱크 낙하, 방패 등은 시나리오 1 이 다루지 않는다.
- `cycles=fixed 30000` 은 임의로 정한 값이다. FAST_COMPUTERS=off 의 BogoMips 분기는 이 환경에서 측정하지 않았다.
- 호스트 부하가 매우 커서 에뮬이 느려져도 tick 은 에뮬 시간이라 영향이 없을 것으로 보이나 부하 조건에서의 시험은 하지 않았다(확인 못 함).
- 개인 정보 주의: 진단 중 화면 캡처 한 번이 사용자의 다른 창을 찍었으나 즉시 삭제했고 이후 호스트 화면 캡처 방식은 폐기했다.

## 9. 엔진 대조 결과 (2026-11-16)

- **시드**: RNG 상태 배열(DS:0xEA12, idx DS:0xEC06)을 덤프에서 읽어 R250 을 거꾸로 되돌려(`w[i]^=w[j]` 역연산) 초기화 상태를 찾고, Borland LCG 첫 3출력으로 시드를 역산. 골든 = **50045** = (1995-06-04 10:30:21 UTC unix 하위 16비트 35645) + 14400(=4h, Borland 기본 TZ 가 EDT) . 초 +1 이면 시드 +1(22→50046, 40→50064, 55→50079 확인).
- 라운드 시작(색 선택) 전에 원본이 소비한 난수: 골든 10573회(타이틀/메뉴 등, 시각 의존으로 재현 불가). 엔진은 `createGame({seed, rngSkip})` 로 같은 상태에서 시작한다.
- 불일치 원인(ENGINE 쪽): ① 놀이장 경계(좌 3/우 w-4/상 24/하 h-4)와 동굴 두 번 걷기의 범위 ② 라운드 시작 난수 소비 순서 ③ 탱크 패드/슬롯 알고리즘 ④ 포신 끝·초기 속도의 0.55 x 보정 ⑤ 비행 dt(PLAYBACK_TIMING) ⑥ Tunneling ⑦ 분화구 x 보정 ⑧ 흙 낙하 경계. 시드 매핑(④)은 원인이 아니었다.
- 결과: 지형 354열 전부, 탱크 위치·각도, 경로 픽셀 269/269, 폭발 위치, 분화구+낙하 후 지형 일치. 자동 테스트 `tests/diff.test.js`(골든 파일만 읽음, `npm test` 포함).
- 한계: 비동 시나리오는 이 1건(+ 지형 시작 위치만 확인한 3건). HUD 바람 화살표 스프라이트(x179~185,y239~245)는 비교에서 제외. 하늘 렌더(별 등)가 소비하는 난수는 엔진에 없음(별 하늘 시 지형 시작 위치가 ~170회 어긋남). 사망 폭발 순서·반경은 미확정(원본 킬 루틴 3191:0100~0261 에는 분화구 호출이 보이지 않음, 화면 효과 후 즉시 실행으로 보임). 산(.MTN) 지형은 파일 선택 순서·창 위치 미검증.

## 11. 사망 연출 variant 와 Tunneling 확대 (2026-11-17)

### 11.1 scenario_003 일치
- 어느 variant 인지 확정: D2 덤프의 DS:ECC0..ECC6(= 69, 338, 112, 414)이 D1 에서는 0 -> variant 9 의 3451:016f 가 쓰는 갱신 영역(탱크 (91,376) 기준 ±22, ±38)과 일치. 같은 덤프의 DS:50D8=1(variant 8 재추첨 조건), DS:EF46=0(지연용 rand 없음), EF34=36044.
- 난수 대조: D1 의 R250 상태(DS:EA12, idx DS:EC06)에서 이후 난수를 뽑아, variant 가 9 로 나오는 위치마다 엔진 구현을 돌려 비교 -> **D1 직후 4번째 난수(앞 3개는 흙 낙하의 rand(1))에서만 0 불일치**, 다음 후보는 51 불일치. 즉 구현이 정확할 때만 한 위치에서 완전 일치.
- 이 과정에서 찾은 엔진 오류: ① 사망 연출 중심이 방패 중심(y−3)이었음 -> 탱크 레코드 (x,y)(171b:00a2) ② 원판이 `u²+v²<=R²+R` 근사였음 -> EXE 중점 원 알고리즘(3c70:09ca)의 행 반폭(R=10 만 우연히 같았음). 둘 다 수정(`terrain.js discRows`, `shot.js _deathFx`).
- 테스트 정렬: 원본은 D1 시점 R250 이 시드에서 11765번째, 엔진은 11767번째(엔진의 플레이 순서 셔플 2회 `rrBase`/`_order` 가 추정 구현이라 원본보다 2개 더 씀). `tests/diff.test.js` 는 엔진 R250 상태를 원본(11765)으로 맞춘 뒤 발사해 variant 9 가 나오는 것까지 확인한다. 이 2개 차이의 원인(원본이 언제 순서를 정하는지)은 확인 못 함. **열린 항목: 알려진 2회 어긋남(추정 셔플, 미해결).** 테스트는 발사 직전 엔진 R250 이 11767번째임을 먼저 단언해(`rng.state()` 비교) 자연 경로가 바뀌면 즉시 드러나게 한다.
- 원본이 이 샷에서 쓴 난수 706개 중 variant 9 가 쓴 것은 121개. 나머지(비행·폭발 연출 등)의 소비 내역은 엔진이 재현하지 않는다(엔진 402개).

### 11.3 Tunneling
- 예외(엔진 추정): 열추적(heat) 유도탄은 터널링하지 않는다. 유도 모델이 매 스텝 속도를 GUIDE_SPEED 이상으로 되돌려 0.75 감쇠가 누적되지 않아 어떤 지형도 관통(재현: 두께 20px 벽 뒤 탱크를 그대로 명중)하기 때문이며 원본 근거는 없다.
- 1a4a:1657 판정과 +0x4a 설정(1a4a:0a1e..0a7e)을 읽어 확정: Tracer·Roller·Dirt Charge 만 +0x4a=0(터널링 안 함), 나머지 모든 투사체 무기는 0xFFFF(터널링). 엔진은 이전에 "표준 폭발+비분열"만 적용했으므로 범위를 넓힘. 접촉 신관은 DS:1C76 으로 계속 제외.
- 검증 한계: 골든은 Baby Missile 1건뿐이다. 다른 무기의 터널링 결과(폭발 위치)는 원본 실행과 대조하지 못했다(인벤토리 지급 자동화 실패 §10). `npm test` 의 기존 무기 시나리오 테스트는 통과.
