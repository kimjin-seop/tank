# 원본 연출 재생 타이밍 (Scorched Earth v1.5)

작성일 2026-11-16. 목적: 클라이언트(`public/js/game/playback.js`, 엔진 1 tick = 20ms 가정)가 원본과 같은 속도로 포탄을 재생하도록 수치를 확정한다. 근거 표기: **확인됨**(EXE 정적 분석), **실측**(DOSBox-X 에서 측정), **추정**, **확인 못 함**.

## 1. 결론 (클라이언트용 한 줄)

> **포탄 비행: 엔진 1 tick(적분 0.02s) = 실시간 약 11.7ms (원본은 우리 재생보다 약 1.71배 빠름). `TICK_MS = 20` → 비행 구간만 `20 / 1.71 ≈ 11.7`.**

- 이 값은 DOSBox-X(cycles=fixed 30000, 486)에서의 **실측 1회 환경** 값이다. 원본 설계상 기계 속도에 거의 무관하도록 자기 보정되지만(§2.3), 보정 상수 K 가 CPU 의 명령 비용 비율에 의존하므로 **실제 486/펜티엄 기계의 값은 확인 못 함**. 설계식 R = 1.825/K 이고 K≈1.06(DOSBox) 이므로 실기계에서는 대략 1.4~2.2배 범위일 수 있다는 것이 "추정"의 전부이다.
- 폭발·흙 낙하·탱크 낙하 등 연출은 **실측하지 못했다**(§4). 이 구간의 `delay()` 는 정적으로 보면 사실상 무력화되어 있어(추정) 원본 속도는 CPU/그리기 속도에 종속이며, 배율을 제시할 근거가 없다.

## 2. 비행 루프 (확인됨 + 실측)

### 2.1 지연 방식: 스텝당 `delay()` 가 **없다**

- 비행 루프는 `while (live_projectiles > 0) step();` 형태이다(3249:01c7, 3855:0218 → `1a4a:0b1f`, 투사체 전체 1 스텝). 스텝 사이에 타이머 대기 호출이 없다(확인됨(EXE)).
- 따라서 **실시간 스텝 시간 = 그 기계에서 한 스텝(FP 계산 + 픽셀 그리기/지우기 + 충돌 판정)을 돌리는 CPU 시간**이다.
- 속도를 맞추는 장치는 "적분 시간 간격 dt 를 기계 속도에 맞춰 바꾸는 것"이다(1a4a:01c4, 투사체 생성 시마다 호출):

```
s  = FIRE_DELAY(DS:0x5140) * BogoMips(DS:0x1c86) / (live_projectiles(DS:0x1c78) * 100.0)
dt = 1 / (50*s);  gravStep = 50*G / s;  windStep = wind / (40*s)     (s>0 이고 DS:0x50f0 == 0 일 때)
dt = 0.02, gravStep = 50*G, windStep = wind/40                           (DS:0x50f0 != 0 또는 s<=0 일 때)
```

### 2.2 `DS:0x50f0` 의 정체 정정 (확인됨(EXE) 23a1:0712, 3249:0172)

기존 `REVERSE_ENGINEERING.md` §3.3 은 `DS:0x50f0` 을 "FAST_COMPUTERS" 설정값으로 적었으나 실제는 다르다.

- 설정값 `FAST_COMPUTERS` 는 `DS:0x50ee`(기본 OFF, 설정 로더 12a5:0e3f 근처).
- `DS:0x50f0 = (DS:0x50ee != 0) && (살아있는 탱크 중 사람(유형 0)이 없음)`. 매뉴얼 "컴퓨터끼리만 싸울 때 속도를 올린다" 와 일치.
- 즉 **사람이 한 명이라도 있으면 FAST_COMPUTERS 설정과 무관하게 `50f0=0` → dt 는 항상 `1/(50 s)`** 이다. dt=0.02 분기는 "컴퓨터끼리만 남은 FAST_COMPUTERS=ON 상태" 전용이다.
- 실측 확인: 골든 시나리오(사람 2명, `FAST_COMPUTERS=on`) 덤프에서 `50ee=1, 50f0=0`, `BogoMips=299`, `s=299`, `dt=6.689e-5`(=1/(50·299)), `gravStep=0.033445`(=10/299), `windStep=0.004097`(=49/(40·299)). 즉 골든 궤적은 dt=0.02 가 아니라 dt≈6.7e-5 로 적분된 것이다. (`ORIGINAL_DIFF_TESTING.md` §1 의 "dt 0.02 정본 분기" 서술은 정정 필요. 엔진 dt=0.02 는 연속 궤적의 거친 근사이며 픽셀 단위 차이가 날 수 있다 — 이 문서 범위 밖, 리스크로만 기록.)

### 2.3 BogoMips (확인됨(EXE) 1a4a:00c3, DS:0x1c86)

- 시작 시 1회: 타이머 틱 `DS:0xee78` 이 20번 증가하는 동안 (a) 15회 함수 포인터 호출 루프, (b) 50회 FP 곱셈·덧셈 루프를 몇 번 돌렸는지 센 값의 합(`DS:0x1c84==0` 일 때; 아니면 (a)×2).
- **타이머 틱 `ee78`**: 게임이 PIT 를 재설정한다(3b59:0063 를 23a1:00a3 이 인자 200 으로 호출). PIT 카운트 = 65536/200 = 327 → 1193182/327 ≈ **3649Hz**(0.274ms/틱), ISR(3b59:0000) 이 `ee78` 를 증가시키고 200틱마다 원래 BIOS 핸들러(18.2Hz)로 체인한다. 따라서 BogoMips 측정 창 W = 20 / 3648.87 = **5.481ms**. 덤프에서 `ee76=200`, 틱당 BIOS 간격 201~202 `ee78` 틱으로 확인(실측).
- 정리하면 BogoMips ≈ W 동안 돈 "교정 루프 반복 수의 합" (DOSBox 실측 299).

### 2.4 스텝당 실시간 (실측)

식: 한 스텝 실시간 T_step, 시뮬레이션 시간 속도 R = dt / T_step = 1 / (50·s·T_step) = 2·live / (FIRE_DELAY · BogoMips · T_step).
T_step ∝ live(루프가 투사체 수만큼 돈다)이므로 **R 은 투사체 수와 무관**(각 투사체가 같은 속도로 날아감).

**측정 방법**: `HARNESS.COM` 의 `dump` 항목은 INT 16h 폴링 시점에 찍히고 "직전 키 이후 N BIOS tick 경과" 일 때만 실행된다. 게임은 비행 중에도 키를 폴링하므로, ENTER 직후 `dump` 의 대기를 w=1,2,3 tick 으로 바꿔 3회 돌리면 비행 중 서로 다른 시점의 투사체 레코드(DS:0xCEB8 → 0x6c바이트 레코드, `vy` +0xC)를 읽을 수 있다. 스텝 수 n = (vy0 − vy)/gravStep (점성 1.0, vy0=(int)(sin·power)), 같은 prefix 라 위상이 같다. 시나리오: 골든 prefix + 각도 45 + 파워 1000 + ENTER.

| 대기 w (BIOS tick) | 덤프 시점 스텝 n | 인접 차이 |
|---|---|---|
| 1 | 1106 | |
| 2 | 2511 | +1405 |
| 3 | 3922 | +1411 |

- 1 BIOS tick = `ee78` 201~202 틱 = 55.0ms(게임이 PIT 를 재설정하므로 BIOS 18.2Hz 체인이 0.2% 빠름, 덤프로 확인).
- **1408 스텝 / 55.0ms = 25.6 스텝/ms → T_step ≈ 39 µs.**
- dt = 6.689e-5 s → **R = 6.689e-5 / 39.06e-6 ≈ 1.71 시뮬레이션초/실초**.
- 교차 검증: 설계식에서 BogoMips·T_step = 299 × 39.06µs = 11.68ms ≈ 2.13·W, 즉 한 스텝 ≈ 교정 루프 1.06회 분량(K=1.06) → R = 1.825/K ≈ 1.72 (FIRE_DELAY=100, live=1; BogoMips≈2W/T_루프 가정) 로 실측 1.71 과 일치.
- 이후(w=4) 구간은 비행이 끝나 비교 불가(해당 덤프는 착탄 후), 파워 80/500 단발 덤프(n=2727/2626 부근)도 같은 규모(기술적 추정 일치, 위상 불명이라 보조 자료로만).

### 2.5 FIRE_DELAY 의 효과

- 시간 모델: R ∝ 1/FIRE_DELAY. FIRE_DELAY=100(기본)에서 R≈1.71. FIRE_DELAY=50 이면 약 3.4배, 200 이면 약 0.86배, 0 이면 `s=0`(`s>0` 조건 불충족) → dt=0.02 분기로 가서 **기계 속도 그대로**(지연 없음, 가능한 한 빠르게)(확인됨(EXE), 실측 안 함).
- `1a4a:29b6` 에도 `FIRE_DELAY` 사용처가 있으나(`vy += 1e? / FIRE_DELAY` 형태) 용도는 확인 못 함.

## 3. 타이머 대기 `delay(ms)` 의 실제 길이 (확인됨(EXE) 정적 분석 / 효과는 추정)

- 게임의 모든 대기는 Borland `delay()`(0000:9af6)이다. 구현: PIT 채널 0 카운터를 읽어 `ms × DS:0xC95C` 만큼 카운트가 흐를 때까지 대기하며, **카운터가 감소해 되감길 때마다 65536 카운트가 흐른 것으로 센다**. `DS:0xC95C=2386`(덤프, 카운트/ms, PIT 모드 3 은 클록당 2 감소).
- 그런데 게임이 PIT 를 327 카운트 주기로 재설정해(위 2.3) 카운터가 0.274ms 마다 되감기므로 되감김 1회가 65536 카운트(=27.5ms 분량)로 계산된다. 결과 실제 대기 ≈ `(⌊ms·2386/65536⌋ + 1) × 0.274ms` (±1회):

| 호출 인자(ms) | 공칭 | 추정 실제 |
|---|---|---|
| 5, 10 (`FALLING_DELAY` 기본 10 포함), 20 | 5~20ms | 약 0.27ms 이하 |
| 100 | 100ms | 약 1.1ms |
| 1000 (`FALLING_DELAY` 최대) | 1000ms | 약 10ms |

- 즉 공칭값의 약 1/200~1/90 로 줄어든다. 이 결론은 코드 해석에서 나온 **추정**이며 DOSBox 에서 delay 실제 길이를 재지는 **못했다**. (`delay()` 가 `SCORCH.DOC` 설명과 달리 거의 효과가 없다는 뜻이라, 맞다면 `FALLING_DELAY` 옵션도 사실상 무의미하다 — 반드시 실측으로 재확인 필요.)

## 5. 클라이언트 적용 제안

1. `public/js/game/playback.js` 의 `TICK_MS=20` 은 유지하되, **투사체 이동(`addPath`의 `rate`)만** `rate = 20/11.7 ≈ 1.71` 로 재생하면 비행 구간이 원본(DOSBox 환경)과 같아진다. 폭발·낙하 등 다른 구간은 근거가 없으므로 현행 유지.
2. 실기계 속도 불확실성이 크므로(§1) 배율은 설정값(기본 1.71)으로 노출해 조정 가능하게 두는 것을 권고.
3. 확정이 더 필요하면: (a) `cycles` 를 바꿔(예 15000/60000) 같은 측정을 재실행해 R 이 보정으로 일정한지 확인(자기 보정 가설 검증, 아직 안 함), (b) INT 1Ch 타이머 후크 기반 샘플러를 하네스에 추가해 폭발·낙하 구간을 직접 재기.

## 6. 한계·확인 못 한 것

- R=1.71 은 DOSBox-X 2026.10.01, `cputype=486`, `cycles=fixed 30000` 단일 설정의 값. `cycles` 변경·실기계는 측정하지 않음. BogoMips=299 는 이 환경 값.
- 측정은 TRACE=on, FLY_SOUND=off, SOUND=off 설정. 소리·트레이스 그리기가 스텝 시간에 주는 영향은 분리하지 않음(비행 중 투사체 그리기·지우기는 포함됨).
- 덤프 시점이 BIOS tick(약 55ms) 경계에 맞는 폴링이라 시각 오차가 있다. 단, 같은 prefix 로 w 만 바꿔 **인접 차이**를 썼으므로 위상 오차는 상쇄되고 두 차이가 1405/1411 로 0.4% 이내 일치.
- 폭발 프레임 간격, 흙/탱크 낙하 속도, 롤러·네이팜 속도: 측정 못 함(§4).
- 비행 중 투사체 `vx` 가 `cos(a)·power` 보다 작게 관측됨(예: 파워 500/각 45 → 0.17s 시점 vx≈−184). 원인 미규명(타이밍 결론과는 무관하게 위치/중력 변화로 n 을 교차 확인했음). 엔진-원본 비교 시 주의.
- 재현 도구: `_reference/tools/diff/probe_flight_gen.py`(w=1..6 시나리오·샌드박스 생성; 작업 폴더에 `sbx_w*` 생성), `probe_flight_read.py`(덤프 시리즈 → 스텝 수·시간), `probe_proj_dump.py`(투사체 레코드 읽기). 측정은 `C:\DOSBox-X` 를 다른 이름의 exe 로 복사해 별도 작업 폴더에서 실행(`run_scenario.sh` 가 `taskkill dosbox-x.exe` 를 하므로 동시 실행 충돌을 피하기 위함). 원본 EXE 는 에뮬레이터 안에서만 실행.
